## 状态机 / 服务端正确性

- **hook/技能触发后必须检查 `g.pending` 是否被调用方无条件覆盖，不能假设"触发完就该轮到我收尾"**：`triggerHook(...)`（尤其是 `onLoseEquip` 这类会挂起新响应的钩子）执行后，如果调用方紧跟着无条件 `g.pending=null;` 之类的收尾代码，会把钩子刚挂起的新状态原地冲掉。正确写法是拍一份 `pendingBefore` 快照，触发后比较 `g.pending!==pendingBefore`，变了就 `return`、把收尾推迟到这个新挂起的响应问完之后（凌统【旋风】反复踩过这个坑，从"独立失去装备入口"到"杀结算中途失去装备"各出现过一次，是这个项目里复发率最高的一类 bug）。
- **姐妹函数容易在扩展一个的时候漏掉同步更新另一个**：`finishGuicai`（郭嘉鬼才改判）和 `finishGuidu`（张角鬼道改判）处理的是同一类"判定被换牌后怎么接回原流程"的问题，新增一种判定类型（比如悲歌/雷击）接入其中一个时，必须记得另一个也要补上对应分支——两处漏掉过至少两次，且是那种"不抛异常、只是静默走错分支/算错效果"的隐蔽 bug，不会被常规测试自动发现。
- **`normalize()` 里判断某个 pending 字段是不是脏数据时，先问"这个字段在这条链的每一个阶段都必然有值吗"**——"还没选/还没填"是合法中间态，不是数据损坏；同理，"数组长度为0"（如某个候选队列已经排到最后一人、变成空数组）经常是合法的边界状态，不能想当然当成脏数据清空。这条已经导致过多个技能从上线起 100% 不可用（陈宫明策、贾诩乱武）。
- **对"数组类型"字段的 normalize 校验，先想"这个字段的创建点会不会传空数组"——会的话必须先补默认值再校验，不能把"字段整个缺失"直接判成脏数据**：Firebase Realtime Database 不保留空数组，创建时 `xxx: []` 的字段同步回来后整个消失（undefined），如果校验写的是 `!Array.isArray(d.xxx)` 且没有先补 `if(!Array.isArray(d.xxx)) d.xxx=[];`，这个合法初始状态会被当场误杀清空 pending，而且**本地 vm/jsdom 测试永远测不出来**（内存 stub 不做 Firebase 序列化）。这条是"Firebase 不保存空数组"坑在 normalize 校验写法上的具体化：项目里至少 `xuanfengPick` 的 targets/discardedCounts、`guhuoQuestion` 的 questioners/answered、`guiduAsk` 的 askedSeats 三处先后踩过，前两处已修、第三处（2026-08 张角鬼道）又复现了同一个模式——**新增带数组字段的询问型 pending 时，检查创建点是否为 `[]` 初始值，是则在 normalize 里先补默认、再从非法判定里去掉这一条**。
- **循环型"轮流问下一个候选人"的响应函数，必须在每一个"问完了、不再继续问"的分支里显式把 `g.pending` 置空**，不能依赖下游代码"进来时应该已经是 null"这个假设——忘了置空会留下一个孤儿 pending，一路带进后续完全不相关的回合。
- **三方 `git merge` 冲突可能把两条分支各自独立、各自正确的修改叠加成一个错误组合**，不是任何一次单独 commit 写错了代码。排查这类"看起来两次独立修复都对、合起来却错了"的症状，用 `git log -p -L` 逐版本追溯到具体哪次合并，而不是假设一定是某次提交本身的问题。
- **响应类 `pending` 缺调用者身份守卫（`g.pending.xxx!==mySeat` 判断）是反复出现的一类漏洞**：新增任何"某个座位被服务端问一个问题、要给出响应"的函数，必须在函数开头校验发起调用的 `mySeat` 就是这个 pending 里记录的、真正该回答的那个座位，否则任何在场客户端都能替别人做决定（这个项目里至少在挑衅/散谣/曹冲称象4个函数/志继/蛊惑质疑等处独立出现过同一类缺口，且修法高度一致：一行 `if(g.pending.xxx!==mySeat) return g;`）。
- **自己包一层 `tx()` 的函数，绝不能被其它 `tx()` 回调内部直接调用**：真实的 `gameRef.transaction()` 每次调用都是"从服务端当前已提交状态取一份独立快照交给回调，回调返回值再整体覆盖服务端状态"——这中间还有真正的异步网络往返。如果一次 `tx()` 回调内部又同步发起另一次 `tx()`（嵌套调用），内层拿到的快照是"外层事务还没提交时的旧状态"，内层先提交，外层稍后用自己的返回值整体覆盖——如果外层的返回值没有正确吸收内层刚做的修改（比如嵌套调用点忘了 `return`，外层套的又是 `fn(g)||g` 这种"没拿到有效返回值就退回原始 `g`"的兜底逻辑），外层提交时会把内层刚写入的状态推进整体覆盖掉，两个事务互相踩踏。张角【鬼道】的 `askNextGuidu`（commit 45a36c5）就是这个模式的真实案例：`triggerGuidu`/`cancelGuidu` 本身已经身处 `tx()` 回调内部，又直接同步调用自带 `tx()` 包裹、且没有 `return` 的 `askNextGuidu`，导致判定牌换不掉、界面卡住。**架构约束**：如果一个函数需要同时支持"作为顶层动作被 UI/机器人直接调用"和"被其它处理流程在事务内部调用"这两种场景，只能选后一种写法——接收 `g`、直接修改、`return g`，不发起新事务；顶层调用方自己在最外层套一次 `tx()` 就够了，不能每一层都各自包一层（参照 `finishGuicai`/`continueBiyueCheck` 这些"接回被打断流程"的辅助函数，全项目绝大多数同类函数都是这个写法，`askNextGuidu` 是目前发现的唯一一处反例，已修复，全项目排查未发现第二处）。

## 隐藏信息

- **投影给某个视角/某个消费者的数据结构要"从头只塞进它真实该看到的字段"，不是"先给完整对象再事后过滤/删字段"**：后一种写法一旦新增字段容易忘记同步过滤，前一种写法从结构上就不可能塞进不该出现的东西（`buildBotVisibleState` 给 AI 机器人投影游戏状态、`canSeeRole` 判断身份可见性都是这个原则的具体应用）。
- **判断某个衍生/聚合数据（比如一个由多次公开事件累加出来的分数）算不算隐藏信息，要看它的每一条输入是不是结构性公开的**，不是看它存放的位置（存在共享状态 `g` 里不等于是隐藏信息）——只要每个判断分支读的都是任何玩家理论上都能通过观察公开日志/公开状态推导出的东西，这个聚合结果本身就不算隐藏信息，可以放心暴露给需要它的消费者。

## 测试方法论

- **单一执行流的轮询测试造不出真正的并发竞态**：需要两个真正独立的事件源（比如"另一名玩家的操作"和"这个机器人自己的一次异步AI调用"）才能触发的时序 bug，用同一个循环反复轮询、只调时间参数是永远撞不出重叠窗口的——正确做法是"真实驱动主流程 + 在已知的关键决策点确定性注入合成并发状态"，不依赖运气。
- **审查别人的代码改动（外部贡献者PR/合并进来的提交）时，即使 commit message 和 diff 看起来只涉及某个功能，也要用真实调用/dump 验证过一遍再下结论**，不能只靠读 diff 判断"看起来对"——这个项目里审查外部贡献者提交时，曾经独立发现过一个和审查目标完全无关、但恰好在同一批代码里的真实 bug（一处变量名遮蔽导致的 TDZ 崩溃）。
- **测试脚本自身的坑，已反复踩过、值得每次写新测试前先检查一遍**：①用 `'x' in obj` 判断"某个键是否存在"和判断"某个键的值是否为 `undefined`" 是两件不同的事——对象字面量里写了 `key: fn(...)` 这种语法，属性名恒存在，`in` 运算符测不出"值其实是 undefined"这件事；②在已经生成的 JSON 字符串上用简单正则（如 `[^}]*`）去抠某个嵌套对象里的字段，一旦中间穿插了别的花括号（如内层的 `equips:{...}`）会被提前截断——需要先 `JSON.parse` 出结构化对象再读字段，不要在拼好的字符串上做正则手术；③vm 沙箱里用 `let`/`const` 声明的顶层变量，不能用 `sb.变量名=值` 这种属性赋值去改（那是往 global 对象加了一个新属性，和脚本作用域内真正的绑定是两个不同的存储位置），必须用 `vm.runInContext('变量名=值;', sb)` 这种裸标识符语句。
- **压缩写在一起的内联 `firebase.database().ref(){return{...}}` stub，多层嵌套花括号在单行/几行内写得太紧凑，容易产生括号匹配歧义导致的 `SyntaxError`**——这个项目的 vm 沙箱测试脚本反复出现过同一个语法错误，修法是把这个 stub 拆成正常缩进的多行写法，不要为了"看起来紧凑"把好几层 `return { ... }` 压在一起。
- **"共享引用"式的 `gameRef.transaction` stub 结构性检测不出嵌套 `tx()` 类问题**：项目里绝大多数测试文件用的 stub 是"每次 transaction 都把同一个 JS 对象引用直接交给回调"（`gameRef={transaction:function(fn){return fn(_g);}}`），回调对它的就地修改立刻对所有持有同一引用的代码可见，不存在"快照"和"提交"两个独立阶段。这和真实 Firebase 的行为不一样（见上面"自己包一层 `tx()` 的函数"那条），意味着"内层 tx 先 commit、外层 tx 后 commit、外层用没吸收内层修改的旧快照覆盖回去"这类竞争，在共享引用 stub 下测不出来——内外层操作的是同一份数据，任何一层的原地修改都立刻互相可见，返回值对不对根本不影响最终对象的内容，测试会"看起来通过"，是假阴性。这不代表过去用旧 stub 跑过的测试结论不可信，只是这一整类 bug 对旧 stub 来说本来就是不可见的，不需要因此重新审查所有历史测试。真正需要验证"一个 `tx()` 回调内部同步调用了另一个可能包含状态推进逻辑的函数"这类场景时，要用 `test-tx-stub.js` 里"快照隔离"版本的 stub（每次 transaction 从独立的 `serverState` 深拷贝快照给回调、回调返回值整体覆盖 `serverState`）——张角【鬼道】那次（commit 45a36c5）就是用这个新 stub 才第一次真实测出问题（同一段测试代码换了 stub，从"3/3 通过"变成"3/3 检测到 bug"）。
- **测试辅助工具（mock/shim/stub）本身可能破坏被测对象，产生的假象和真实缺陷长得一模一样——写探针/shim 时，探针本身也要先证伪，不能只顾着验证被测代码**：本地机器人服务可行性评估那次，给最小 DOM shim 套了一层 `Proxy`（想借此侦测"渲染期间访问了 shim 未实现的属性"），结果这层 `Proxy` 本身把渲染破坏了，导致十几个原本渲染正常的 phase 在探针报告里显示成"渲染出 0 个按钮"——看起来和被测代码里的真实渲染缺陷（shim 缺某个 API 导致按钮渲染不出来）完全同一种症状，如果不去復核就会被当成十几个新发现的 bug 记录下来。识别方法很简单也很有效：把新加的这层工具（这里是 `Proxy`）去掉，同样的测试立刻恢复正常——"去掉这层新加的辅助设施后现象消失"就是"问题出在辅助设施本身、不在被测代码"的直接证据。以后每次新增或修改探针/shim/mock 这类测试基础设施后，第一反应应该是"这层新东西本身有没有可能已经改变了被测对象的行为"，而不是直接采信它报告的结果去写结论。
- **一批看起来在多个独立位置上都出现的"结果整齐划一地异常"，几乎总是意味着探针/测试工具本身的某个共享环节出了系统性错误，而不是被测系统真的在那么多独立位置都出了同一种真实 bug**：真实的、彼此独立的缺陷很少会呈现出完全一致的失败模式（不同代码路径的 bug 通常表现各不相同）；反过来，"9 个毫不相关的 phase 全部在同一步骤上报告同一种失败"这种整齐划一的模式，本身就是一个强烈信号——大概率是测试代码里某个所有用例共享的环节（比如共用的沙箱初始化、共用的桩函数、共用的断言辅助函数）写错了，而不是被测系统凑巧在 9 个地方都坏成了同一个样子。同一次评估里复现过两次：一次是全部 phase 报告"没有渲染出任何按钮"（根因是共享的 shim 初始化里那层破坏性的 `Proxy`，见上一条）；另一次是全部 9 个"三重保护"验证用例都报告"专用分支没有真正提交动作"，根因是验证脚本把计数用的 `gameRef` 挂成了沙箱的一个属性，而 `game.js` 里 `let gameRef` 是脚本作用域的绑定、会遮蔽掉这个同名属性——所有用例共用同一段挂载逻辑，于是全部失效。看到这种"整齐划一"的模式时，正确的第一反应是去检查测试代码自己的共享部分，而不是逐个排查被测系统的这些位置分别错在哪。

## 前端 / UI

- **座位卡/目标选择这类"点击即触发技能结算"的按钮，渲染条件必须完整复刻服务端真正的 `canTarget` 全部校验层，不能手写一份简化版**——手写简化版容易漏掉某个具体的目标限制（比如某个角色的免疫技能），渲染出一个点了会被服务端拒绝的死按钮；正确做法是直接调用 `CARD_PLAYS[x].canTarget(...)` 这个和服务端共用的同一个函数，而不是在渲染层重新写一遍判断逻辑。
- **裸 `g`/`window.g` 引用导致的运行时崩溃，是"点击没反应"类问题里和"数据层损坏"并列、但经常被忽略的另一个排查方向**：普通玩家看不到浏览器控制台，前端未捕获异常和数据同步问题造成的"静默无反应"从症状上完全无法区分，必须靠真实 dump（或至少真实调用一遍对应函数）才能分辨，不能默认往复杂的数据层方向猜。（这条本身已经是 `CLAUDE.md` 规则24，这里只是提醒它属于一个更大的排查方法论：遇到"点了没反应"，先把"前端是否抛出未捕获异常"和"数据层是否正确"当作并列的两个假设分别检验，不要预设是哪一个。）
- **搭建 Playwright 等需要真实浏览器的环境时，如果沙箱里没有预装完整依赖、又没有 root 权限**：可以用 `apt-get download` 把缺失的共享库（如 `libnspr4`/`libnss3`/`libasound2t64`）下载到本地目录解包、`LD_LIBRARY_PATH` 指过去，不需要 `sudo apt install`——这个项目多次复用过这个方法。

## AI 机器人集成专属

- **全局并发/去重标志（如"某个决策正在进行中"这类布尔开关）如果只有"丢弃重复请求"、没有"丢弃之后要不要补一次检查"，新增触发源之后大概率会撞上隐藏的架构缺口**：这类标志引入时要主动设计"错过了的请求怎么办"这一步（比如记一个"是否有被丢弃的、状态确实不同的请求"的标志，清空主锁后立即补查一次），不能假设"以后不会有别的触发源"。这个项目的 `botDecisionInFlight` 就是从"只有两个内部触发点、从未真正丢过"到"新增外部触发点后立刻大概率撞上"的真实案例。
- **AI（LLM）的输出永远不能直接信任，必须走和真人输入完全同一套合法性校验**：AI 给出的选择只能是"从服务端已经用真实规则筛选好的候选列表里选一个 index"，不能让 AI 自己"发明"一个座位号/牌名/参数；解析失败、索引越界、格式不对，一律归为同一类"AI 没有给出合法答案"，静默回退到本地已有的启发式兜底逻辑，不重试、不特殊处理、不让游戏卡住。
- **"候选列表 + 让 AI 选 index"是这个项目里 AI 决策接入的统一模式，不要为每个新决策点各自发明一种新的 AI 响应格式**：不管是选牌、选目标、还是要不要发动某个技能，都统一构造成"一份带序号的候选数组 + 一句只要求返回 `{"choice": 数字}` 的 prompt"，解析逻辑（`parseBotPlayAiChoice` 这类）可以跨决策点直接复用。
- **给 AI 的 prompt 里塞入某个数值型的内部状态（比如一个由公开事件累加出来的分数）之前，先想清楚"给分档描述性文本"还是"给裸数值"**：裸数值离开了它的内部刻度定义就没有意义（LLM 不知道这个数字的合理区间是什么），分档成"较强/一定/无明显倾向"这类自然语言描述通常更可靠，且不需要在 prompt 里额外解释这个刻度怎么换算。
- **一个决策点要不要接入 AI，值得先做投入产出评估再动手，不是能接就接**：这个项目在决定"要不要把 AI 接入 `runBotDecision` 里某个具体分支"之前，先按"有没有真正的策略含量"分类——纯机械/无决策空间的操作不接（AI 决策的延迟和成本换不来任何收益）；有策略含量但影响面小的酌情跳过；只对真正需要判断（隐藏信息下的信任博弈、资源取舍等）的决策点接入。
- **验证 AI prompt 篇幅必须用真实 tokenizer，不能用"字符数/N"这类估算公式**：这个项目早期多次用"约4字符=1token"（英文经验值）估算中文 prompt 的 token 数，得出"342/276/318/426 tokens，远低于600上限"之类的结论——后来用离线真实 tokenizer（`js-tiktoken`（cl100k_base，对应 GPT/OpenRouter 系）、`@anthropic-ai/tokenizer`（对应 Claude）重新核实同一批 prompt，发现中文场景真实的字符/token 比率接近 1.0~1.2（不是4），此前的估算普遍低估了约3~4倍，部分身份局版本的 system prompt 实际已经逼近甚至超出预算。这两个 tokenizer 库都能离线运行（不需要联网调用真实 API），npm 安装后几行代码就能拿到准确数字，成本很低，没有理由继续用字符数估算——以后任何"验证 prompt/文本篇幅是否在预算内"的场景都应该走这条路径。
- **给机器人接上一个此前几乎没人真正触发过的"冷门主动技能"入口，本质上是在对这段代码做一次从未有过的高频压力测试**：此前只有偶尔一个真人手动点一次的代码路径，一旦被机器人反复自动触发，很容易把潜伏已久、从未暴露过的既有 bug（不是这次接线任务本身写错的代码）炸出来。真实案例：袁绍【乱击】的 `confirmLuanji` 长期存在"效果建立的响应 pending 被后续清理代码原地覆盖、`g.aoe` 卡死非空、中央出牌区永久停止淡出"这个 bug，但因为几乎没人主动用这个冷门技能、机器人此前也没有入口触发它，从未被跑到过；直到"机器人主动技能解锁"任务给【乱击】接上了机器人主动发动入口，机器人开始频繁触发，这条路径才第一次被大量执行、症状才第一次被真实观察到。以后再给某个"几乎没人用/机器人从没主动发动过"的技能接机器人决策入口时：①接线本身完成、测试通过之后不代表万事大吉——接线任务的测试覆盖的是"机器人会不会正确调用这个入口"，不等于覆盖了"这个技能的底层实现本身是否正确"，这段实现可能藏着从未被真正验证过的旧 bug，机器人开始高频触发后才是第一次真正的考验；②如果接线之后出现看起来无关的连锁症状（比如"中央出牌区不淡出"和乱击表面上毫无关系），要考虑"是不是新解锁的这个技能的既有实现里藏着一直没暴露的 bug，被这次高频触发第一次真正跑到了"这个可能性，而不是先入为主地怀疑最近改动的那条代码本身（这次一开始怀疑的是 debugLogs 频控逻辑，排查了一圈才发现是完全独立的乱击既有实现问题）；③排查这类"看起来和最近改动无关的连锁症状"时，检查思路应该是：先确认症状是在哪次改动之后才出现的，再问"这次改动本身有没有直接碰这块代码"，如果没有，下一步该问的是"这次改动有没有让某段此前很少被执行到的旧代码第一次被高频执行到"，而不是继续深挖这次改动本身。
