- **【新功能·AI机器人接入 第1阶段/共4阶段】适配层(Claude+OpenRouter) + 大厅密钥输入UI，完全不接入任何游戏逻辑**。目标：给 `bot.js` 现有的本地规则机器人增加一个可选的"用真实AI做决策"模式——房主（`mySeat===0`，和 `addBot()`/`removeBot()` 既有的身份边界完全一致）在开局前粘一把自己的API密钥，本局全部机器人（最多7个）共享这一把密钥、由密钥持有者承担费用；不填密钥则机器人保持现有的本地启发式行为，零功能退化。
  - **确定方案：Claude直连+OpenRouter覆盖其它模型，不加后端（这是设计阶段发现的一个项目定性问题，值得记录）**。设计时用 WebSearch 核实当前 API 密钥格式/CORS 支持现状（不是凭记忆假设），发现一个真实的架构冲突：Anthropic 的 `api.anthropic.com` **官方支持浏览器直连**（`anthropic-dangerous-direct-browser-access:true` 请求头，是 Anthropic 自己文档化的、专门为"用户自带密钥的客户端应用"场景开的口子）；但 OpenAI 的 `api.openai.com` **不支持浏览器直连 CORS**（多个 OpenAI 官方开发者社区帖子证实，官方建议是接服务器代理）——而这个项目是纯静态多文件、无构建流程、只有 Firebase Realtime Database，没有后端（CLAUDE.md 开篇即有明确记录）。这意味着"直接用用户自己的 OpenAI 密钥"技术上不可能实现，除非额外加服务器基础设施，这和项目定性直接冲突。把这个冲突原样呈现给用户、给出三个选项（A：Claude原生+OpenRouter覆盖其它模型，零基础设施变化；B：加服务器代理，是真正的架构变更；C：只支持Claude）而不是自己悄悄决定，用户确认选 **A**：Claude 直连 `api.anthropic.com`；其余模型（含 GPT）一律走 **OpenRouter**（`openrouter.ai`，和 OpenAI 的 Chat Completions 格式兼容、支持浏览器直连 CORS）中转，UI 上必须如实标注"OpenRouter(GPT/多模型)"，不能让用户误以为是在直接用自己的 OpenAI 密钥——持有 OpenAI 密钥的用户需要另外去 OpenRouter 申请一把密钥，这是这个方案确认接受的代价。
  - **密钥安全设计（和这个项目"隐藏信息永不进 `g`"的既有原则同一脉络）**：密钥只存在 **sessionStorage**（本标签页内存级持久化，刷新/关闭标签页即自动清空，天然不需要写清理代码）+ 本文件（`ai-bot.js`）的模块级变量里，绝不写入 `g`/Firebase 共享状态、绝不用 `localStorage`（会跨刷新/跨标签页持久化，超出"这一局游戏"的生命周期，是刻意规避的一种更持久但不必要的存储方式）、绝不出现在任何会被其他玩家读到的地方（座位卡/日志/`pending` 等）。持有密钥的只有触发 `addBot()` 的那个人——`room-lifecycle.js` 的 `addBot()`/`removeBot()` 服务端本来就要求 `mySeat===0`，这次直接复用同一条已有的身份边界，不新发明一套权限判断。
  - **四阶段路线图（当前只完成到第1阶段）**：①适配层+密钥输入UI（本次，零游戏逻辑接入）→②接入 `botPlay`（真正让AI参与出牌决策，未开始，需要用户明确许可才进入）→③扩展到 `botBestTarget`（AI参与目标选择，未开始）→④更大范围/是否要重新评估OpenAI直连代理方案（未开始，暂定为远期可能性，不是承诺）。
  - **本次范围（第1阶段）**：新增 `ai-bot.js`（挂在 `bot.js` 之后、`render.js` 之前，主题上是 `bot.js` 的延伸，但目前两者之间零调用——`bot.js`（`botPlay`/`botBestTarget`/`runBotDecision`/`scheduleBotTurn`）本次一行未改，这是刻意的范围边界）：
    1. `PROVIDER_ADAPTERS`（`claude`/`openrouter` 两项，各自 `{label, endpoint, buildRequest(apiKey,opts), parseResponse(json)}`，纯函数，不发起网络请求；以后新增 provider 只需要在这里加一项，不用碰 `callAI`）——`claude` 的 `buildRequest` 带上必需的 `anthropic-dangerous-direct-browser-access:'true'` 头（没有这个头会被浏览器跨域直接拒绝）；`openrouter` 用 `Authorization: Bearer` 头，请求体格式和 OpenAI Chat Completions 兼容。

    3. `detectAiProvider(key)` — 纯函数，按密钥前缀识别提供商（`sk-ant-`→claude，`sk-or-`→openrouter，都不匹配返回 `null`）。
    4. `renderAiKeyPanel(container)` — 大厅密钥输入面板，由 `render-controls.js` 的 `renderControls()` 大厅阶段（`!g.started`）、`mySeat===0` 分支里在"添加/移除机器人"按钮之后调用（同一次渲染、同一个身份边界）。含费用承担提醒+隐私说明文案、密码类型输入框（`type=password`，防止旁人偷看）、自动识别提供商展示+识别失败时的手动选择下拉框兜底。**面板自身的交互（识别提供商、切换下拉框）刻意不走整体 `render(g)` 重绘**——`renderControls` 每次调用都会 `c.innerHTML=''` 整体清空重建，如果密钥输入框自己的 `input` 事件也去触发整体重绘，会在敲下第一个字符后立即丢失焦点（新生成的 DOM 节点不会继承旧节点的焦点），对密码类输入框是破坏性的；改成面板内部状态更新走局部 DOM 操作，只有"另一名玩家加入房间"这类外部事件触发的 `render(g)` 才会重建整个面板，此时靠 `input.value=aiApiKey` 从模块级变量正确恢复已输入内容（已用 Playwright 真实验证：模拟外部重渲染打断输入，值不丢失）。
    5. sessionStorage 读写：`sgsAiKey`/`sgsAiProvider` 两个键，模块级变量 `aiApiKey`/`aiProvider` 镜像 `game.js` 顶部 `myClientId` 的既有处理方式（加载时 `try{...}catch(e){}` 包裹尝试恢复一次）。**"blur+keydown双重保存兜底"的确认设计里，实现时把字面的 `keydown` 换成了 `input` 事件**（在文件注释里明确写了原因，不是悄悄替换）：`keydown` 在字符真正插入输入框之前就先触发，此刻读 `.value` 会读到慢一拍的旧值，粘贴/输入法候选字也未必逐字触发 `keydown`；`input` 事件在值真正变化后才触发，覆盖打字/粘贴/自动填充全部输入方式，效果上仍是"每次改动都立即保存"这同一个要求，只是技术上更准确。`blur` 作为第二层兜底，两者调用同一份保存逻辑，重复调用无副作用。
