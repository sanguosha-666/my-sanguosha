- **CORE-135(issue #180):手牌数维度的「对方有没有闪/杀」概率预测（A1 第一步）**：外部项目对比分析 A1 项的第一步，**只做手牌数这一个维度**，刻意不碰历史打出行为记录（对方 `LocalAiEngine` 的 `usedSlash`/`usedDodge` 那一层是**正则解析中文日志**，昵称含空格/「对」字就会错乱且无测试保护；我们要做应该做成结构化埋点，涉及新增持久化字段 + `normalize` 防御，是独立的一块工作。分开做才能验证是哪一维带来的行为变化）。**改动前的问题**：`botTargetScore` 的基础分里手牌数只以 `(target.hand||[]).length*2` 的形式**加分**（手牌多=更值得拆）——这对顺手/拆桥是对的，但**对出杀而言方向是反的**（手牌多恰恰意味着更可能有闪、更难打中）；决斗同理，胜负几乎完全由双方杀的数量决定，却完全没建模。

  **概率怎么来的（不拍脑袋，从真实牌堆推）**：对方的公式是 `0.15+n*0.11` 这种线性拍脑袋值（n=8 时算出 1.03，被 `clamp` 硬截住，说明没从牌堆构成推导过）。我们直接用 `buildDeck()` 的实测构成 + 超几何分布 `P(n张手牌中至少一张X) = 1 − C(N−K,n)/C(N,n)` 打表。**实测结果**：N=136，杀系（杀30+火杀5+雷杀9）K=44（32.4%），闪 K=15（**11.0%，比直觉稀有得多**）。两条曲线的性质差异很大且都是牌堆构成的真实反映：闪的概率到 n=12 才 0.654，**整个手牌区间都有分辨力**；杀 n=3 就到 0.590、n=8 之后每格只涨 0.017，**基本饱和**，意味着 duel 维度实际只在 0~3 张这个低区间有分辨力，4 张以上一视同仁——**刻意不为了「让它看起来有用」去人为拉大 duel 的系数**。曲线形状经断言验证：严格单调递增 + 边际增量逐格递减（凹形）。打表而非运行时算，是因为 `botTargetScore` 在每次候选枚举里对每张牌×每个目标各调一次，不能带组合数循环。

  **衰减系数 0.85 的定性（如实记录，不包装成精确校准）**：设计阶段给的三条衰减理由里，「手牌里还混着装备/锦囊」那条**是错的**——超几何本来就是从整副 136 张里抽，装备锦囊已经算在分母里，不该再扣一次。剩下两条方向**相反**（闪会被消耗 → 压低；玩家倾向留防御牌 → 抬高），净效果不确定。而且实测发现**衰减系数几乎不影响行为**：它是乘性的，主要作用是整体平移，而 argmax 比较里常数项会抵消；真正决定行为的是曲线极差，那来自超几何形状本身（0.75/0.80/0.85 三档极差分别 0.38/0.42/0.43，差别很小）。所以 0.85 是一个**温和的保守余量**，不是推导或调参得到的精确修正。

  **n=0 用精确的 0，不套 0.05 下限**：手牌数是**公开信息**，0 张手牌就是确定没有闪，不是「概率很低」；下限 0.05 的本意是「永远别 100% 确定」，那个理由在 n=0 时不成立。下限只对 n≥1 生效（实际从不触发，n=1 的闪已经是 0.094）。

  **边界（记清楚，以后别搞混）：装备区效果不进这张表**。本函数建模的是「**手里**有没有闪/杀」。八卦阵那种「不用牌也能闪」的来源**不在建模范围内**——装备区是**公开信息**，那是已知事实而不是预测，混进来就是把两种性质不同的东西搅在一起。以后要处理八卦阵/技能类免伤，应该单独加一项（读 `target.equips` 直接判，根本不需要概率），**不要来调这张表**。

- **CORE-138(issue #185):强 C 出牌窗口的「状态无变化」检测（引用比较 → `botStateKey` 内容比较）**：来源是对比分析的 A4 项，但**实际做的事情和最初提案完全不同**——提案的「步数上限动态化」被实测否决，最终只做了这一项，issue 标题和范围都按实测结果重写过。

  **修的是什么缺陷**：`runBotActionWindow` 每步提交后用 `if(!newG || newG===lastG)` 判断动作有没有生效。`newG===lastG` 是**引用相等**，而真实 Firebase 的 `tx(fn, onCommitted)` 在 transaction resolve 后交付的是 `snapshot.val()` 的**全新对象**——所以这半条判断几乎永远为假。结果是：`!newG` 能抓住「提交回调根本没来」（`executePlayWindowChoiceAwait` 等到 `BOT_COMMIT_TIMEOUT_MS` 超时 resolve null），但**抓不到「提交确实发生了、却被服务端守卫原地拒绝成 no-op」**——那种情况下 tx 照常 commit 并交付一个语义完全相同的新对象，判断顺利放行，循环于是用一模一样的局面重新枚举候选、选中同一个动作、再次被拒绝……**正是 CLAUDE.md 防复发规则 26 记录过的死循环模式**（「机器人是无状态重算的，被服务端原地拒绝一次就会永久死循环」）。今天靠 `BOT_WINDOW_MAX_STEPS=8` 兜底所以不会真卡死，最坏后果是白白浪费最多 8 次 AI 调用 + 8 次无效提交；但步数上限是**粗筛**不是**检测**——它不知道循环是在正常推进还是原地打转。

  **修法**：循环体开头记下 `stepStartKey = botStateKey(lastG, seat)`（放在循环**内**而不是循环外——每轮都要用当轮真正参与决策的那份快照算，不能沿用上一轮的值），提交回来后比对 `botStateKey(newG, seat)===stepStartKey`，相同即 `stallDetected` 并 break。**两道检查职责不同、都保留**：`!newG || newG===lastG` 逐字未改（抓「回调没来」），新增的 `stallDetected` 抓「回调来了但状态没动」。**为什么 `botStateKey` 够准**：它包含 `(g.log||[]).length`，而本项目任何一次真实生效的动作都会往 `g.log` 追加至少一条记录（出牌/装备/伤害/判定/摸弃牌全都写日志），「日志长度没变」就是「这一步什么都没发生」的可靠信号；再叠加 `phase`/`pending` 各字段/`hp`/手牌数，误杀风险很低。`stallDetected` 也写一条 `bot_decision_failed` 诊断日志（和 `!newG` 同一 kind，但 message 明确区分是哪一种——两种的排查方向完全不同）。

- **CORE-141(issue #194):手机端不跑全屏 Canvas 飘牌动画（平板/桌面维持现状）**：来源是一次手机/平板端耗电分析（分析基线 commit `b0affea`），这是分析中定位到的**最大单项持续耗电源**。**问题**：`game-bg.js` 的 `bgTick` 是全屏 Canvas 的 `requestAnimationFrame` 循环，**整局游戏期间无条件持续运行**（`room-lifecycle.js:90` 进房 `startGameBg()` 启动，只有 `backToLobby` 的 `stopGameBg()` 才停）——画布是 `#gameBgCanvas{position:fixed;inset:0}` 全视口且按 DPR 放大（手机横屏 844×390 @DPR3 → 2532×1170 ≈ 296 万像素），每帧全量 `clearRect`（60fps 下约 1.78 亿像素/秒，高刷屏翻倍），再画最多 18 张卡、每张都要 `save/translate/rotate` + 圆角路径 `fill`/`stroke` + **重设 `ctx.font`（尺寸随机，触发字体重新解析）** + `fillText`（canvas 文字是 2D 上下文最贵的操作之一）。而它是**纯装饰**——文件开头自己写着「纯视觉层：不读游戏状态」。已有的 `visibilitychange` 暂停是对的（切后台不耗电），所以耗的全是**正盯着屏幕玩**的时间，正好是用户反馈的场景。

  **实现结构**：把「该不该跑」的三个条件收敛到 `bgShouldAnimate()`（`bgRunning` 在对局中 / `!isPhoneLayout()` 非手机 / `!document.hidden` 页面可见），再由幂等的 `applyBgAnimationPolicy()` 统一启停；`startGameBg`/`visibilitychange`/`resize`/`orientationchange` 四处全部改走它，避免判定散落各处导致口径分叉。`visibilitychange` 的语义与改动前一致（隐藏则停、可见且在对局中则续），只是多叠了一条「手机不跑」。新增 `orientationchange` 监听：部分移动浏览器旋转时 `resize` 触发时机不可靠，`render.js` 的 `checkLandscapeGate` 也是两个都听，沿用同一惯例。

  **顺带省下的内存**：`sizeBgCanvas()` 会把画布 backing store 按 DPR 放大分配（手机横屏 ≈ **11.8MB**）。手机端既然不画，这块内存就不该占——在正要优化的那类设备上白占 11.8MB 还会加剧 GC 压力。所以把 `sizeBgCanvas()` 也从 `startGameBg` 挪进策略里：不画时画布保持默认 300×150（几乎不占内存），真要开始画时 `applyBgAnimationPolicy` 会先补上。`resize`/`orientationchange` 里也只在 `bgShouldAnimate()` 为真时才重算尺寸，手机端反复旋转不会分配。
