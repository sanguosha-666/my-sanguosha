- **CORE-146 再收尾三项：豁免判据从"按位置"改成"按布局关系" / `.gitignore` 图片规则改为根目录锚定 / 报告需区分实测与推断**：
  - **① 严格间隙断言的豁免判据重构（按位置 → 按结构）**。上一版写的是「双方都在 `.seat-equip-bar` 里就豁免」——**那是按元素在卡里的位置豁免，本质上是清单的变体**：将来别处再出现 9px 堆叠文字（判定区标签、化身行、状态标签……）还得回来手动加一条。真正的判据其实是上一条记录自己得出来的那个**结构**判据：两个元素若是同一格式化上下文里的**流式兄弟分支**，相对位置由正常流决定，前一个长大只会把后一个推开，**结构上不可能重叠**——量到的负间隙必然只是 line-box 名义重叠（行盒高 > 行距），不是布局缺陷；而**绝对定位**的元素脱离正常流、位置由 `top/left` 硬指定，才是真会撞上的那一类。改成 `flowSiblings(a,b)`：找共同祖先 → 取双方在其下的直接子分支（分支相同或缺失＝嵌套关系，不豁免）→ 检查从叶子到分支的整条路径都在正常流里。**新增元素自动归类，不需要维护任何清单。**

- **修复「从主屏启动时画面是放大的」（`pwaResetZoom`）**：用户真机反馈从 standalone 启动时画面带着上次退出时的放大状态。**明确不是「退出后保留对局状态」那件事**——那是期望行为，本次改动完全不碰对局状态，不会跳回大厅。

  - **真正的原因（方向 3）**：iOS 的 standalone web app 把**缩放级别当作 app 状态由系统保留**，下次从主屏启动时一并恢复。所以只要在游戏中双指误触放大过一次，之后每次启动都带着那个放大。页面这边无法阻止系统保留，只能在启动/恢复时主动归零。
  - **为什么不用 `user-scalable=no`/`maximum-scale=1` 一禁了之**：① iOS 10 起 Safari **故意忽略** `user-scalable=no`（无障碍考虑），靠它并不可靠；② 这个项目手机横屏下最小字号只有 9px，彻底禁用缩放会让看不清的人失去唯一的补救手段。所以保留「用户可主动放大看细节」的能力，只在**启动/恢复**这一刻归零。
  - **归零手法**：WebKit 只在 viewport meta 的 `content` **发生变化**时才重新应用缩放约束，所以先临时切到带 `maximum-scale=1.0, user-scalable=no` 的锁定态逼它把缩放压回 1，再在随后一帧（双层 `requestAnimationFrame`）撤回可缩放的基础值。**只设一次相同的值不会触发重新应用**——这一点已用鉴别力实测钉住。
  - **触发时机**：`pwaInit()`（启动）+ `window.addEventListener('pageshow')`（覆盖普通加载与 bfcache/后台恢复）。**刻意不挂 `visibilitychange`**：那个事件每次切回前台都触发，用户主动放大想看清某处细节时切出去接个消息再回来就被强行复位，反而是干扰。**并且带 `pwaIsStandalone()` 守卫**：普通浏览器里页面本来就不保留缩放，复位只会打断用户正在进行的缩放。
  - **验证（4 条新断言 + 2 次鉴别力实测）**：standalone 下先进入锁定态、随后撤回可缩放态（两个阶段都断言——只看最终态根本看不出它做过归零）；普通浏览器下 viewport 一字不动；**归零不影响对局状态**（仍在对局中、7 张对手卡、`phase=play`、没跳回大厅——这是用户点名纠正过的点，专门钉住）。鉴别力：①把锁定态那一步改成「设同样的值」→ 断言变红；②去掉 standalone 守卫 → 普通浏览器那条变红。
  - **⚠️ 真机验证仍未完成**：本机没有真机，且 Playwright 的 viewport 不存在「系统保留的缩放级别」这个概念，**上述断言验的是「归零逻辑是否按预期执行」，不是「iOS 是否真的因此复位了」**。后者必须真机：退出前记录缩放比例 → 从主屏重新打开 → 确认缩放已复位且对局内容/状态没丢。

- **「主屏冷启动画面被放大」重新排查：假设被真机推翻，移除错误修复 + 加真机诊断入口**：
  - **真机结果推翻了上一条的假设**：上一条按「iOS standalone 保留上次退出时的缩放级别」实现了 `pwaResetZoom`。用户真机验证：**即使退出前完全没有双指缩放过（缩放一直是 1.0），从主屏冷启动后画面依然是放大的**。所以放大与上次的缩放状态**无关**，是每次冷启动都会发生的事，那个假设不成立。
  - **已移除 `pwaResetZoom` 及其 `pageshow` 监听**。理由：①依据的假设已被推翻；②它从未被真机证实有效；③它本身是「会不会是这段 toggle 人为造成了一次缩放跳动」这个怀疑方向的嫌疑对象，移除后真机再测一次就能把这一层干净地排除掉。断言同步换成「确认已移除、且 viewport 未被任何代码改动」。
  - **排查方向 2 拿到了本地证据（但还不能下结论）**：页面里确实有多处直接吃视口尺寸的布局计算，而 standalone 去掉地址栏后视口高度会变大：
    - `.seat` 高度是 `clamp(70px, 33dvh, 150px)`（`index.html`），随视口高度连续变化；
    - `cardMetricsForViewport()`（`render-hand.js:363`）按 `window.innerHeight` 分档决定手牌卡宽度，**`h<=520 && coarse` 这一档给 60，跳出后给 88**。
    实测（844 宽、8 人局）：视口高 340→460 时**座位卡从 84×112 长到 113×150（+36%），而手牌卡恒为 66×94 完全不变**；高度跨过 521 时**手牌卡突变 66×94 → 88×126（+33%）**、座位卡反而缩小。iPhone 横屏高度在 390~430 区间，standalone 比 Safari 高出的那几十像素**不会跨过 520 断点**，但足以让座位卡长大十几个百分点，而手牌卡纹丝不动——**视觉上就是「上半部分被放大、比例失调」**。这与「每次冷启动都发生、与上次缩放无关」完全吻合。
    **但这仍然只是一个候选解释，不是结论**：它无法排除另一种可能——iOS standalone 横屏冷启动时 viewport 按竖屏宽度计算再整体拉大填满横屏（那会是真正的等比缩放，`visualViewport.scale ≠ 1`）。两者在肉眼上都表现为「画面被放大」，**必须靠真机数值区分**。
  - **新增 `pwaDiagnostics()` / `pwaDiagnosticsHtml()`，接进 `?` 帮助弹窗底部**：手机上没有开发者控制台、远程调试也不总是有条件，而这个问题只在真机 standalone 下复现——**继续按推断改代码是错的，必须先拿到真机数值**。诊断一次性列出 12 项：运行形态与 `navigator.standalone`、三个 `display-mode` 媒体查询、`window.inner`、`documentElement.client`（layout viewport）、`visualViewport` 的宽高/`scale`/`offsetTop`、`screen`/`avail`/`dpr`、viewport meta 原文、safe-area、关键断点命中情况、`cardMetricsForViewport()` 的计算值、手牌卡与对手座位卡的**实测**尺寸（含座位卡占视口高的百分比）。选 `?` 帮助弹窗是因为它是手机上唯一随时可点、且**不依赖房间**的入口。
    **判读方法（写在函数注释里）**：普通浏览器看一次、主屏冷启动看一次，两组对比——`visualViewport.scale ≠ 1` → 真的是页面被缩放（浏览器层）；layout viewport 宽高不同 → 视口尺寸本身变了（布局层，dvh/断点会跟着变）；`scale=1` 但 `innerWidth` 明显小于 screen 长边 → viewport 按竖屏宽度算了再被拉大填满横屏；上面都正常但 `cardWidth`/座位卡实测尺寸跳档 → 是布局计算吃了不同的视口值，不是缩放。
  - **验证边界**：Playwright 里既没有 iOS 的 viewport 行为、也没有系统状态保留，**测不出那个现象本身**。新加的断言只保证「诊断函数不报错、关键量齐备、确实接进了帮助弹窗」，**数值必须由真机读取**。

- **「主屏冷启动画面被放大」定案：不是缩放，是 `33dvh` 与固定像素手牌卡的比例失配**：
  - **真机数值（iPhone 16 横屏，standalone）**：`window.inner` / `layoutViewport` / `visualViewport` 三者全是 **852×393**，**`visualViewport.scale = 1.000`**，`screen` 393×852（设备自然方向，正常），viewport meta 原文就是 `width=device-width, initial-scale=1.0, viewport-fit=cover`，断点 `max-height:520+landscape+coarse` 命中 ✓，`cardWidth=60`、手牌卡实测 66×94，对手座位卡实测 97×130 = **33.0% 视口高**。
  - **结论：三个排查方向里，1 和 3 被数据直接排除**。`scale=1.000` 说明页面根本没有被缩放（方向 1 的 `initial-scale` 正常生效、方向 3 的「toggle 造成缩放跳动」也不存在——何况那段代码上一轮已经移除）；`inner`/`layout`/`visual` 三者完全一致，也排除了「viewport 按竖屏宽度算再拉大填满横屏」那种等比缩放。**所有数值都完全符合设计**：33.0% 正是 `33dvh`，60/66×94 正是 `h<=520 && coarse` 档的正确值。
  - **真正的原因（方向 2 坐实）**：standalone 去掉地址栏后视口高度从 Safari 的约 310~346 变成满屏 393，而 **`.seat` 是 `clamp(70px, 33dvh, 150px)`（按比例伸缩）、手牌卡是固定像素 66×94（`cardMetricsForViewport` 在 `h<=520` 档恒返回 60）**——两者伸缩方式不同步。用真机的确切参数（852 宽、8 人局）本地复现，结果与真机**逐像素一致**（97×130、33.0%），据此推算 Safari 侧：座位卡 86×114（-12.3%）/ 82×109（-16.2%）/ 77×102（-21.5%），对应地址栏占 47/63/83px。**即 standalone 下座位卡比 Safari 大 12~22%，而手牌卡一个像素没变**——视觉上就是「上半部分被放大、和手牌比例失调」，用户感知为「画面被放大」。这与「每次冷启动都发生、与上次缩放状态无关」完全吻合。
  - **本质是一个设计上的不一致，不是渲染 bug**：座位卡按视口比例伸缩、手牌卡按断点取固定值，视口高度一变两者就失配。三条可选方向（**均未实施，`33dvh` 与 `cardMetricsForViewport` 仍在用户要求的冻结中**）：①什么都不改——standalone 空间本来更大，座位卡大一点是合理的；②收紧 `.seat` 的 clamp（降低 `33dvh` 系数或 150px 上限），让它在高视口下别长那么快；③让手牌卡也随视口伸缩，两者保持同一套比例——这条最治本，但改动面最大（`cardMetricsForViewport` 是分档返回固定值的，要改成连续函数）。同一份数据也解释了此前记录的「底部空白随视口增高从 39px 涨到 59px」，两件事同源，应当一起决定。
  - **顺带修掉诊断自身的一个缺陷**：`safe-area` 那项在真机上四个值全是 `?`——第一版读的是 `--sa-top` 这类 CSS 变量，而项目里**从来没有定义过**这几个变量，等于一条读不到任何东西的诊断项。`env()` 只能在 CSS 属性值里求值、拿不到 JS 变量，改为造一个临时元素把四个 `env()` 写进 `padding`、再读回 computed 值（JS 侧唯一能拿到 safe-area 实际像素的办法），并补了一条「必须是可解析的长度值」的断言钉住。

- **手牌卡改为按视口比例伸缩，与座位卡统一伸缩逻辑（「主屏启动画面被放大」的最终修复）**：
  - **根因回顾**：`.seat` 是 `clamp(70px, 33dvh, 150px)`（按比例伸缩），手牌卡却是写死的 `66px × 94px`（固定像素）——**两者伸缩逻辑不统一**。真机实测 iPhone 16 横屏：Safari 的 layout viewport 是 852×303、从主屏启动（standalone，无地址栏）是 852×393，差 90px；于是座位卡按比例长大 21.5%，手牌卡一个像素没动（算上 Safari 自身 1.066 的缩放，手牌卡在屏幕上反而**小了 6%**）——一个变大一个变小、差 27 个百分点，看起来就是「上半部分被放大了」。**不是缩放问题**：standalone 的 `visualViewport.scale` 实测 = 1.000，且 `inner`/`layout`/`visual` 三者完全一致。
  - **用户选定的基准（重要，决定了改法方向）**：**不压座位卡去迁就 Safari，而是让手牌卡跟上**。理由是 standalone 多出来的 90px 是真实可用空间，应该被利用而不是裁掉；根因是两者伸缩逻辑不统一，就该把这个不一致修掉，而不是让 standalone 去将就 Safari 那份更局促的高度预算。硬约束：**Safari 侧数值一个像素都不许变。**
  - **实现**：`.hand .card` 改成 `--card-h:clamp(70px, 31dvh, 132px)` + `height:var(--card-h)` + `width:auto` + `aspect-ratio:66/94`，`--badge` 改成 `calc(var(--card-h) * 0.17)`（= 16/94）。**系数取 31dvh 是从「Safari 档不变」反推的**：31dvh × 303 = 93.9 ≈ 原来的 94px。宽度用 `aspect-ratio` 而不是再写一条 clamp——两条 clamp 各自取值时在边界处可能对不上，宽高比会悄悄漂移。
  - **`cardMetricsForViewport()` 同步改成连续函数**（只改 `h<=520 && coarse` 这一档，其余各档维持原有的「按视口分档返回固定值」写法），公式与 CSS 严格一一对应。**顺带修掉一处早就存在的 JS/CSS 漂移**：这一档改动前恒返回 `cardWidth:60`，而 CSS 实际是 `66px`——`fitFontSize` 一直按一个偏小的宽度在算牌名字号。改成同源公式后两边一致（Safari 档 66/66、standalone 档 86/86），并加了断言防止再次漂移。

- **CORE-147（issue #204）：【桃园结义】不再对满体力角色开启无效的无懈轮询**：
  - **问题**：`startTaoyuanWuxie` 的跳过循环只跳过「不存在/已阵亡」，满体力角色照样往下走——对他开一整轮无懈询问（`phase='wuxie'` + `openWuxieRound`），一直到 `finishTaoyuanTarget` 才由 `hp<maxHp` 判断出「体力已满」、什么也没发生。

- **CORE-158（issue #217）：已下架模型（`cerebras:zai-glm-4.7`）每次决策都被重复请求**：
  - **现象（用户实测）**：`AI调用失败(provider=tri,model=cerebras:zai-glm-4.7):other - HTTP 404: {"code":"model_archived"},耗时约2374ms`。
  - **先排除了一个看似显然的方向**：默认池**早就修好了**——`DEFAULT_CEREBRAS_MODELS` 和 `DEFAULT_TRI_MODELS` 里都已无该模型，且有注释「2026-08-20 实测 /public/v1/models：zai-glm-4.7 已下架」。所以不是「默认值忘了更新」，而是下面两个成因叠加。
  - **成因 A：`hydrate` 时不校验历史选择是否还在当前池里**。`ai-bot.js` 从 sessionStorage 读回 `aiApiModels` 时只判断「是不是数组」，而默认填充只在**列表为空**时才生效。用户在模型下架前勾选过该条目，之后代码把它从默认池移除，但**用户的旧勾选被原样恢复、继续参与轮换**。修法：与当前 provider 的池取交集，剔除失效条目。**刻意取交集而不是整体丢弃**——用户可能勾了 9 个只有 1 个失效，整体回落默认会白白覆盖掉其余 8 个的有效选择；交集为空才回落默认（由既有的 `length===0` 分支接手）。
  - **成因 B：404 不写冷却，而 tri 恰好是「优先级扫描、刻意不轮转」**。写 `_modelCooldowns` 的条件只覆盖 `429 || 413`；而 `resolveAiModel('tri')` 的注释原文是「不记 round-robin 指针——『优先使用 cerebras』要求可用时永远选它，而不是轮流」。两者相加：`cerebras` 是最高优先级、该模型又永不进入冷却 → **每一次决策都重新选中它、重新吃一个 404**，用户实测每次固定浪费约 2.4 秒，AI 能力等于完全没生效（每次都回落 `localFallback`）。修法：把 404 且响应体含 `model_archived`/`is archived` 的情形纳入冷却写入条件。
  - **与 429 的本质区别决定了冷却时长**：429 是**临时**限流、过一会儿能恢复，按 `retry_after` 冷却几十秒是对的；`model_archived` 是**永久**失效，本会话内不可能变回可用。新增 `ARCHIVED_MODEL_COOLDOWN_SEC = 365*24*3600`，等价于「本会话内不再选它」，但仍走既有的 `_modelCooldowns` 机制，**不新造一套"永久黑名单"状态**（轮换、空串哨兵、UI 展示全部原样复用）。同时用新增的 `dropArchivedModel()` 把它从 `aiApiModels` 摘掉并落盘——只改内存的话，同一标签页刷新后又会从 sessionStorage 读回来重踩。**刻意不动 `aiApiModel`（手动单选）**：那是用户显式指定的唯一模型，静默改掉等于替用户做主，应由 UI 提示后让用户自己换。
  - **错误分类细化**：新增 `reason:'model_unavailable'`，不再混进笼统的 `other`。已确认 `reason` 在全项目只用于**拼接展示文本**、没有任何分支依赖具体值，因此新增分类是安全的。`bot-ai-bus.js` 的失败信息相应给出可操作提示（「该模型已被 provider 下架，已自动从本次轮换池移除并改用其它模型；如需彻底更换请在密钥面板重新勾选」）；全池冷却的文案也从「限流冷却」改为「限流/不可用冷却」——冷却原因现在不止限流了。
  - **实施中自己造了两个假绿，如实记录**：①`callAI(provider, apiKey, opts)` 需要**三个参数**，第一版测试只传了两个（`provider` 实际拿到的是 prompt 字符串），冷却分支根本走不到——连带那条「破坏性验证 PASS」也是假的（改坏与不改坏都没写冷却，`resolveAiModel` 自然都返回第一个）。②`check()` 第一版是纯同步的，而 `callAI` 返回 Promise、断言在 `.then` 里，**异步断言失败会变成 unhandled rejection 而不是 FAIL**。两处都修正后才是真结果。另外 storage 键名一开始用正则从源码动态提取、提错了键（拿到 `sgsAiKey` 当成 `sgsAiModels`），改为硬编码 + 一条防漂移断言（键名改动时本测试立刻失败）。
