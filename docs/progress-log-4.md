- **横屏骨架级重建（landscape-ui）第1阶段：座位卡渲染，支持最多7人局的视觉展示**——这是一次信息架构级重建，不是渐进式调整。目标支持最多7人局（对应最多6个对手同屏横排），采用参考图驱动的设计：座位卡从"头像居左+信息居右"改成"标题栏（武将名+血量数字+"?"说明入口）+ 头像 + 身份/势力占位行 + 血量红心图标 + 装备紧凑标签"纵向堆叠结构，对手行不再用 grid 环绕布局（旧的 `.seats`/`.opp1`/`.opp2`/`seatSlot()` 整体废弃），改用简单的 flex 横排（`.opp-row`），人数弹性靠 `flex:1 1 0` 平分，不需要为不同人数维护不同的 grid 模板。

  **可读性下限的推导（用 Playwright 真实渲染截图验证，不是拍脑袋定的）**：用统一公式 `每张卡宽度=(设备宽度-40内边距-8×(对手数-1)间距)/对手数`，对 iPhone SE横屏(667px)/iPhone12·13横屏(844px)/iPad横屏(1024px) × 2~7人局（1~6个对手）共18种组合逐一手算，中途一次因为复制粘贴贴错行数字被用户当场核对出不一致（"1个对手=587px"其实是"6个对手那一行的可用宽度分子"），重新逐行摊开计算过程后确认全部一致，最坏情况是"7人局在SE横屏"：97.83px。这个数字本身也没有直接采信——用真实静态HTML mockup分别测过"含身份文字行"（100px）和"去掉身份文字行后"（97.83px精确宽度）两版，后者反而因为少一行、每行分到更多垂直空间而看起来更清晰，确认"去掉身份/势力占位不会让可读性下限变紧、只会更宽松"这个判断成立，90px下限（留约8px安全余量）不需要因为这次确认身份留空而重新收紧。实测结论：**2-7人局在这三档代表性横屏宽度下都不需要触发横向滚动**，`overflow-x:auto` 只作为安全网保留，不是预期会触发的主路径。

  **身份/势力两个字段这次数据模型里都没有**（身份局系统未实现），渲染层画一个空壳 `<div class="seat-identity"></div>` 占位，不造假数据，等真正的身份局/势力系统做出来再回填内容——这是设计阶段就明确排除的范围，不是遗漏。参考图右侧"托管/荣誉/背包/任务/菜单"五个功能按钮同样明确排除，不做任何占位UI。

  **`renderSeatCard(g, seat, isSelf)` 具名函数提炼**：`render.js` 里原来那段~90行内联在 `render()` 里的座位卡视觉生成代码（CLAUDE.md 文件拆分排查时曾专门标注过的"从匿名回调提炼具名函数"候选项，当时因为"性质不同于纯重构、需要单独决策"而暂缓），这次借着整体重写顺手提炼——**理由是这次是真正的整体重写，"零行为变化"这条约束天然不适用（不管提不提炼，新内容都要从头验证正确性），提炼不产生任何额外的验证成本，纯粹是免费的**。函数只负责"这张卡片长什么样"，目标选择/技能发动的交互逻辑（读那~15种技能各自的客户端选牌状态机变量，约300行）**没有一并搬进去**——和 `render-hand.js` 拆分时"这批状态不是手牌专属、不搬"是同一个原则，这批交互代码仍留在 `render()` 里，通过新提炼的 `buildSeatDOM(i)` 内部函数（创建DOM+调用`renderSeatCard`生成视觉结构+接上原有交互逻辑）衔接。

  **对手在行内的顺序**：从"我"的下家开始按回合顺序排列（`oppOrder`），单独一整行的横排场景下比旧版"回合顺序上离我近的分左右两侧"（`seatSlot`）更直觉，不需要为不同人数维护不同的分侧规则，`seatSlot` 函数本身已删除。

  **`.avatar-box`/`.avatar-placeholder`（选将阶段候选卡片仍在使用）刻意不与新座位卡共用**：新座位卡的头像容器是"占满卡片宽度+aspect-ratio:3/4+信息在下方"（新起类名 `.seat-avatar`），选将候选卡片是"侧边固定宽度+信息在旁边"（`.avatar-box`），两者尺寸约束方向相反，硬要共用同一个类名会互相冲突——分开定义，`.general-pick-card` 完全不受这次改动影响。

  - **关键设计取舍：常驻的台面背景，和牌内容本身的淡入淡出，必须是两个独立的视觉层，不能揉进同一个 opacity 开关里**——`.table-card` 的核心机制（阶段0/1早就有，这次完全没动）是靠 `opacity:0`+`.show`/`.exchange-mode` 两个 class 控制"这批牌什么时候显示、什么时候淡出"；如果直接把背景画在 `.table-card` 自己身上，背景会跟着牌一起在空闲时归零、消失不见，达不到"这是一条常驻区域"的效果。**解法是新增一层纯静态的外层包装 `#tableStrip`**（`index.html` 里的一个新 `<div>`，不参与任何 JS 状态、不被 `render-table.js` 引用），背景/上下分隔线/最小高度全部画在这一层；`#tableCard` 原样嵌套在它内部，id、class、`render-table.js` 里读写它的全部逻辑一个字都没有改动，只负责"这批牌具体长什么样、什么时候淡入淡出"——两层各司其职，互不覆盖。
  - **坐标基准复用 `#game`，不需要再迁移一次**（阶段1完成时就已经和用户核实过这一点：`#game` 是 Stage2 全部涉及元素——`.opp-row`/`#tableStrip`/`#tableCard`/`#meSeat`/`.hand`——共同的祖先容器，`render-table.js` 的飞牌/连线坐标计算只要求"能找到一个同时包含出牌方座位和这批牌自己的公共祖先"，不关心 `#tableCard` 内部套了几层包装）。这次新增的 `#tableStrip` 只是在 `#tableCard` 外面多包了一层纯展示的静态 div，没有改变 `#tableCard` 相对 `#game` 的祖先关系，所以 `render-table.js` 两处 `getElementById('game')` 调用不需要任何改动——这正是阶段1时向用户确认过的"这个基准是 Stage2 也会复用的，不是临时补丁"这条结论的兑现。
