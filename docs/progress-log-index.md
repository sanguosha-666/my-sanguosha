## 二、验证与排查的方法论教训（比具体 bug 更值钱）

- **假修复识别**：症状消失 ≠ 问题解决。CORE-146[12] 把手牌图标 `position:absolute` 挪到右侧后
  "重叠消失"，dump 坐标才发现 `.seat-bottom` 才是定位上下文、图标被推出了卡片外——
  它只是**跑出了检测视野**。**修完要量的是"目标量本身"，不是"报警有没有停"。**
  同类：曹冲称象[5] 先证伪了"Firebase/normalize 数组序列化"这个最初怀疑的方向，才找到真根因。
- **代理指标选错，两次**：①装备条渐变的几何估算（"4 行约占卡底 37%"）实测是 43.7%，
  本能反应是加深渐变去迎合数字，但真正在乎的量（实测对比度 7.11）本来就达标——
  该修的是那条估算错的注释（CLAUDE.md 规则 21）。②CORE-146[11] 势力字描边先用"白像素比例"
  当指标，六个方案全落在 18.4~18.7%、**零鉴别力**，换成"势力色可见度"才分得开（72.1…38.3）。
  **写下任何中间指标时都要清楚它只是代理；和实测打架时先怀疑代理。**
- **断言的价值全在"能变色"**：永远绿和永远红一样没价值（`inside()` 用了 DOMRect 不存在的
  `.w/.h` → 恒 `NaN` 恒 false；装备条背景断言在设计变更后验证了一个已不成立的命题却继续返回通过）。
  **新断言必须先看到它红**；**设计变更后必须回头检查旧断言的命题是否还成立**。见 CLAUDE.md 规则 20。
- **别漏掉整个维度**：横屏重建做了多轮响应式验证，但全项目当时**没有一条 `@media (max-height)`**，
  所有样本在"高度"这一维上统一宽松，直到真机反馈才发现一屏装不下近 3 倍内容。见 CLAUDE.md 规则 22。
- **验证样本要挑最刁钻的**：已知刁钻样本清单（最长武将名`颜良文丑`、最长装备名`青龙偃月刀`、
  最亮/最暗立绘、最小卡片、装备 4 槽全满、**最大 maxHp=6**）在 CLAUDE.md 规则 18。
  CORE-146[12] 把单点验证扩成 5 人数 × 3 视口矩阵后，**立刻抓到一个单点测不到的缺陷**（🔖 撞装备条）。
- **测量结果差了数量级时，先怀疑工具**：CORE-138[11] 连续三次测量错误（hook 被覆盖、
  setter 重包装导致嵌套重复计数、分组 key 跨局碰撞）产出过"每张牌 123 步"这种数字，全部作废重测。
- **"看起来能复用"必须先 grep 完整实现**：左慈开发时 `respondHuashenPick` 表面可复用，
  读完函数体才发现守卫写死了 phase、收尾会级联整局重新初始化。见 CLAUDE.md 规则 28。
- **规则数值别凭记忆转述**：曾以为"按点数循环触发"该抄郭嘉遗计，grep 后发现遗计根本不循环，
  真正做这件事的是荀彧节命。**动手前先核实官方卡面/既有实现。**

## 三、几个"刻意不做"的决定（别当成待修 bug 重新排查一遍）

- **手牌/身份不做真隐藏、数据库权限全开**：朋友局定位，见 CLAUDE.md 一节「产品定位与边界」。
- **铁索连环推进时中央出牌区不显示牌面**：需要把牌对象存进 `g.tiesuoQueue` 跨函数传递，
  是设计层改动，已知且刻意不修。
- **2 人局的卢导致"够不着"不加特例**：符合真实规则，可用拆牌/丈八反制。
- **平板允许纵向滚动**：设计如此，对平板套用"必须一屏装完"是错的口径——那条断言会永远红。
- **`run_startgame_wiring_test.js` 场景4 有已知的低概率 flaky**：候选池切片与 `debugPickGeneral`
  碰撞，与被测改动无关，遇到重跑一次即可。
