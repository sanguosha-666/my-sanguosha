- **桌面端页面整体自适应：2~8人局在常见桌面分辨率下完整显示在一屏内，不需要滚动条**。用户反馈的现象是"8人局装不下"，但**规划阶段用 Playwright 真实测量先纠正了这个前提**：1440×900下，`assignSeatZones` 把对手区行数上限钉死在3行（6/7/8人局总行数完全相同，超过6人只是在已有的第2/3行里插右列，不新增行），且**2人局（只用1行对手区）本身就已经溢出188px**——真正的病根是"整个页面从来没对视口高度做过预算，每个区块都是auto高度堆叠"，不是单纯"人数多导致溢出"。方案确认后复用项目里"手机横屏矮视口"（`@media(max-height:460px) and (orientation:landscape)`）已经验证过的同一套方法论，分三步实现，全部在 `#game.desktop-layout`+`@media(min-width:1024px)` 双重限定的作用域内，不影响任何既有的移动端响应式规则。
  - **步骤a：座位区域尺寸驱动方向反转**。base rule（`.seat{width:...;aspect-ratio:3/4}`）是"设宽度、靠 aspect-ratio 反推高度"——桌面宽屏下没问题，但纵向预算紧张的场景下会让高度完全不受控。反过来：新增 `render.js` 的 `computeOppZoneRowsUsed(playerCount)`（对应 `assignSeatZones` 的分区规则，1/2/3档）+`updateDesktopSeatHeights(g)`——和既有的 `updateLogPanelHeight()` 同一套"JS量出实际渲染位置、回写内联style"模式（调用时机也一样，必须排在 `renderControls`/`renderHand` 完成之后），但比它多一层复杂度：桌面下对手区行数本身是变量（1~3档，取决于人数），不能像手机横屏那次直接套一个固定的 `dvh` clamp（那次对手区永远只有1行）。CSS 侧只清空会和"JS设height"打架的 `flex/min-width/max-width` 约束，不写死height——height完全交给JS按视口余量动态算。
  - **步骤b：压缩剩余固定开销**。座位区自适应后，标题栏(`h1`/`.sub`)/信息条(`.panel.table`)/武将名行(`.hand-label`)/页脚提示(`.footnote`)这批和人数无关、全程固定auto堆叠的开销依然存在——完全复用手机横屏断点已经用过的同一批压缩手法（只是数值上不用像手机断点那么极限，桌面横向空间依然宽裕，紧张的只是纵向）：`.wrap:has(#game.desktop-layout:not(.hidden))` 收紧 padding+标题字号+隐藏 `.sub`；`#game.desktop-layout:not(.hidden) ~ .footnote{display:none}`（和手机断点 `#game:not(.hidden) ~ .footnote` 同一原理，多加 `.desktop-layout` 限定避免命中<1024px的窄屏正常游玩场景）；`.panel.table`/`.phase-pill`/`.banner`/`.controls`/`.hand-label` 各自收紧padding/字号/margin。**作用域统一用 `:has(#game.desktop-layout:not(.hidden))`/`#game.desktop-layout:not(.hidden) ~`——两个条件（宽屏+已开局）缺一都不生效**，大厅阶段和窄屏正常游玩都维持原来宽松的样式，和移动端断点的既有隔离原则一致。
  - **步骤c：真实测量迭代收敛，过程中连续暴露并修复了5处测量/公式坑，每一处都是先测出真实溢出数字、定位根因、再修复，不是拍脑袋调参数**：
    1. 步骤b上线后 `updateDesktopSeatHeights` 里"用 `.footnote.getBoundingClientRect().bottom` 当内容边界"直接失效——`.footnote` 被步骤b隐藏后 `display:none` 元素的 rect 全部返回0，让公式误判"对手区下方毫无内容"，把几乎整个视口余量错误分给对手区，6/8人局溢出反而从135px恶化到412px。改用 `#meSeat`/`#hand`（桌面grid最后一行，任何情况下都会真实生成盒子）的最大 `bottom` 代替。
    2. 改用 `#tableStrip` 的 `top` 当"对手区下方从哪开始"的界桩后，发现 `#tableStrip` 自己有 `align-self:center`（在row2/3合并空间里居中而非贴顶）——这意味着它当前的 `top` 位置本身循环依赖"row2/3(即left/right座位卡)现在有多高"，正是要求解的量本身，导致结果偏保守（算出92却被90的地板夹住，视口还剩128px完全没用上）。
    3. 改成"加总 `.panel.table`/`myGeneral`/`.hand-label` 各自border-box高度、行间距一律假设8px grid row-gap"——这个假设是错的：`.panel.table` 有 `margin:0 0 6px`，`.hand-label` 有 `margin:6px 0 4px`，这些CSS margin会叠加在grid的row-gap之上（grid不会吸收/合并它们），导致算出的可用高度比实际需要的更宽松，6/8人局溢出40px。
    4. **最终修法（真正解决了②③两类问题）**：不再假设/加总任何具体padding/margin/gap数值，改成直接测量"对手区当前(不管此刻是什么尺寸)实际渲染到哪里结束"(取全部座位卡里最大的 `bottom`，不用 `#tableStrip` 这种会自我居中、依赖对手区高度的元素当界桩)到 `contentBottom` 之间的距离——这是安全的**位置差测量**，不是循环依赖：row4~7这几个元素都是 `align-items:start`（容器默认值，均未覆盖），会随对手区(rows1-3)增高/变矮整体同步平移，彼此之间的间距（含各自CSS margin）保持不变，所以"此刻对手区多高"不影响这段差值本身的准确性，天然包含全部真实margin/padding/gap，不需要手动枚举。**通用结论：位置差测量对"随参考点整体平移"的元素是安全的，只有像 `align-self:center` 这种"在给定空间内自我居中"的布局才会引入真正的循环依赖——分辨这两种情况，而不是一律回避位置测量或一律信任位置测量。**
    5. 收敛到8px级小溢出后，又发现两处残余：`.wrap` 在步骤b新增的 `padding-bottom:10px` 在 `meSeat`/`hand` 的rect之外、不会被 `contentBottom` 捕捉到（改成 `getComputedStyle` 动态读取，不硬编码10这个数字）；`#oppTopRow`（row1）比 `#oppRow` 的left/right座位卡（row2/row3）多出自己的 `padding:8px 8px 4px`（12px），旧公式假设三行平均分摊预算，这12px只属于row1却没被单独扣除，导致算出的每行高度系统性偏大12px（改成动态读 `getComputedStyle(oppTopRowEl).paddingTop/paddingBottom` 单独扣除，不硬编码12）。

  - **调整方案（维持"8人局一屏不溢出"约束不变）**：
    1. 中央列从 `1fr` 改为 `minmax(300px,420px)`（上限 420px 仍能舒适容纳约5张牌一行，更多靠既有 `flex-wrap` 优雅换行，真实测过7张牌的最坏场景不重叠、不横向越界）；`#game.desktop-layout` 加 `justify-content:center`，四列全部改成有上限的 `minmax` 后不再强制撑满 `#game` 全部可用宽度，多出的横向空间变成左右对称的留白（而不是塞给某一列造成"该列自己也很空"）。
    2. `#meSeat` 不再是脱离共享预算的固定值——扩展 `updateDesktopSeatHeights()`（`render.js`）联立求解两个未知数：设对手座位高度为 `h`、`meSeat` 高度为 `ME_SEAT_RATIO(1.25)*h`（保持"我的卡必须比对手更大更醒目"这条既有规则——`verify_stage1_seatcard.js` 锁定的回归——但改成和对手区成比例，而不是绝对固定值），代入同一条总预算方程直接解出 `h`：
